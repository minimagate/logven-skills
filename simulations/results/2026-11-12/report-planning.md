I would make the report form the single place for unsaved edits, save only through explicit actions, and give saved columns stable references to dataset fields. The dashboard would display the same report results through a separate read-only view.

The supplied code explains the current failures:

- `Report#preview` calls `update!`. `ReportsController#show` invokes it from a GET request authorized as `show?`, so opening a preview changes the saved report using only read permission.
- The editor copies only the outer configuration object. Its column array and column objects remain shared with the source; adding or removing columns can therefore change the original client object. Ordinary changes also save immediately when `options.live` is true, while column additions and removals skip that path.
- Columns are stored by editable name, although dataset fields already have stable IDs and row data uses those IDs. A field rename can disconnect a saved report from its data.
- `copy()` submits the source report object, potentially including its identity and ownership. The server's `copy!` copies saved configuration rather than explicitly representing the current unsaved form. Neither boundary defines which attributes a new report may inherit.

My proposed behavior is:

1. **Preview keeps edits in memory.** Keep `show` read-only and remove its parameter-driven update. Use the existing server-rendered report form, normal Rails assignment, and nested attributes for columns. A preview submission assigns permitted values to a loaded report in memory, validates them, and renders the form with its preview. It never saves, including on success. Add, remove, reorder, and field changes all submit the same current form state. Invalid input retains the user's entries and shows an error rather than silently displaying the previous result.

2. **Save and Save a copy are explicit choices.** Updating the original goes through the ordinary report update action. Saving a copy builds a new report in the authorized destination workspace using the current form's settings, creates fresh column children, and saves everything in one transaction. It retains the source dataset reference, but never copies report IDs, column IDs, timestamps, or ownership supplied by the browser. A failed copy retains the form and leaves the source unchanged. Previewing needs no persisted draft record, draft token, or parallel JavaScript state.

3. **Columns point to fields, not names.** Introduce a small `Report::Column` child record with `report_id`, `field_id`, `position`, and `width`. The field supplies its current name and kind. Validate the width/order and require each selected field to belong to the report's dataset; require the report and dataset to belong to the same workspace. Foreign keys and indexes protect references. Keep arbitrary row values in `Row#data` JSON: those values really are dynamic. The supplied excerpt does not define filter and sort shapes, so I would not invent new tables for them in this change. Keep their current storage behind explicit permitted keys and validation, and use stable field IDs wherever they reference fields.

4. **The dashboard reads a saved report.** Its existing item or widget should reference the saved report, rather than copy its configuration or mount the editor. Reuse a read-only result partial and a small report-owned result query for both the editor preview and dashboard. That query uses the report's current in-memory settings and never saves. The editor supplies its assigned model; the dashboard supplies the saved model. Do not add dashboard/live/read-only flags to the editor or teach the query which page called it. The shown `preview` currently returns all dataset rows; the actual filtering/rendering code is absent, so implementation must connect the existing query behavior if present rather than create a second engine.

This means renaming “Revenue” to “Net revenue” updates the displayed label while the report still reads the same field ID. Renaming is safe; changing a field's kind may invalidate a filter or sort, so that should produce a clear configuration error while preserving the report. For deletion, I would initially block removal of a field referenced by saved report columns and explain which reports need adjustment. This is smaller and safer than silently dropping report columns. Any filter or sort references must receive the same deletion protection. A dashboard whose report becomes unavailable should show an unavailable state without exposing its data or deleting its reference.

Permissions remain server-enforced through Pundit. Use explicit workspace URLs, load the workspace through the user's accessible workspaces, and load each report through that workspace. The session may choose an initial destination, but must not silently decide which workspace an operation owns. Authorize show for reading, update for saving, and the editor's preview permission using the same edit-access rule. Copy requires permission to read the source and create a report in the destination; it does not require changing the source. Dataset access and workspace consistency must also hold. Dashboard access alone never grants report or dataset access: check those permissions when rendering, including after access is revoked.

Implementation would have three small slices:

- **Fix persistence and request boundaries:** replace the mutating preview, add a dedicated preview resource and copy resource, and keep ordinary updates separate. Use explicit parameter lists instead of `permit!`. Editing existing columns preserves their nested IDs and destruction markers; creating a copy builds fresh children from the resulting active definitions and does not accept those identities as new-record attributes. Verify that preview and copy leave the source unchanged, copy includes unsaved edits, update saves explicitly, failures write nothing, and unauthorized/cross-workspace requests are denied.
- **Stabilize saved columns:** add the child table, associations, validations, and references. Backfill separately from the structural migration, resolving old names only against each report's own dataset. Missing or ambiguous names must be reported for repair rather than guessed or discarded. Keep old storage readable during the transition; switch consumers and remove the legacy column configuration only after reconciliation. Verify rename stability, ordering/width preservation, dataset ownership, and deletion behavior.
- **Connect the form and dashboard:** replace the shallow draft/save callbacks with normal server-rendered form submissions; remove the dashboard's editor import. Reuse only report results, keeping editing controls in the form. Check preview, save, copy, column additions/removals/reordering, invalid input, and dashboard display manually in the real browser, including keyboard use and narrow screens.
