I’d make experimentation private to the open form and save only when someone chooses **Save as copy**. The copy would have its own report settings while using the same dataset. That assumes you want a different view of the data, rather than a frozen copy of the data itself.

The supplied code explains two ways edits escape: preview calls `update!` on the saved report, and the JavaScript editor copies only the outer configuration object, leaving its column array shared. Columns also store editable names instead of the stable field IDs the dataset already provides, so a rename can break the connection.

1. **Preview without saving.** Build a separate, unsaved report from the source, apply the submitted settings and render the preview through the existing server-rendered form. Adding, removing and reordering columns should all update that preview. Invalid input should keep the person’s edits visible with an explanation. Cancel discards the experiment; refreshing or leaving may lose it. Persistent drafts can wait until there is a real need to resume work later.

2. **Give columns a reliable identity.** Make report columns owned records with a field reference, position and width, rather than name-based entries in configuration JSON. Display the field’s current name. Use stable field references for filters and sorting too, with ordinary validation of their supported settings. Keep arbitrary dataset row values in JSON, where their dynamic shape belongs. Normal Rails models and nested forms can then handle edits without a second JavaScript draft system. During editing, preserve column identities and explicit removals; when copying, create fresh report and column identities while retaining references to the existing fields.

3. **Make saving deliberate and protected.** “Save as copy” creates the new report and its settings together, or saves nothing if validation fails. It never updates the source. Check both access to the source and permission to create the copy using Pundit; derive the workspace and dataset on the server and reject fields or child IDs belonging elsewhere. Replace `permit!` with explicit permitted settings. Keep the dashboard’s read-only display separate from the editing form; share the report query/rendering contract without giving the dashboard an editor that can save.

I’d first remove preview writes and shared mutable editor state, then introduce stable column records and convert existing settings, and finally connect and check the copy flow. Keep schema changes separate from the data conversion. Before switching existing reports over, check which old names resolve uniquely to fields; renamed, missing or ambiguous names need an explicit repair path. Preserve their old settings until conversion is verified rather than silently dropping columns.

The key checks would prove that previews and structural edits leave the original unchanged, copies remain independent, field renames preserve selections, invalid submissions retain edits, and unauthorized or cross-workspace requests cannot read or create reports. Inspect the form and dashboard manually in a running app, including failed saves. Use domain, policy and HTTP-effect tests rather than markup or browser tests.
