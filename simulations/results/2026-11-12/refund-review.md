1. **[P1] Scope invoice lookup to the authorized account — `lib/refund_endpoint.rb:8`.** Authorization checks the authenticated route account, but `InvoiceRepository#find` searches globally and the endpoint never verifies `invoice.account_id`. An operator permitted to refund account 1 can supply an invoice ID belonging to account 2 and refund its charge. I reproduced this with permissions that allow only account 1: the gateway received the account-2 charge and the endpoint returned 202. Load the invoice within the authorized account or reject an ownership mismatch before calling the gateway.

2. **[P1] Convert amounts using the invoice currency's exponent — `lib/refund_endpoint.rb:9`.** The provider requires the currency's smallest unit, but the endpoint always multiplies by 100. For supported currencies, my probes sent 2,000 units for JPY 20 (expected 20) and 123 units for KWD 1.234 (expected 1,234). This requests incorrect refund amounts. Use the documented exponent for `invoice.currency` when converting to an integer amount.

3. **[P1] Preserve the gateway connection failure — `lib/refund_endpoint.rb:12`.** `PROVIDER.md` explicitly says `IOError` means no refund was accepted, whereas 202 means it was accepted for processing. Rescuing that error as 202 therefore tells clients a refund is underway when nothing will process it; there is no queued retry in this implementation. A gateway probe raising `IOError` returned 202 with no accepted refund. Propagate the failure or return an appropriate failure response so callers can report it and retry.

4. **[P2] Avoid floating-point truncation of money — `lib/refund_endpoint.rb:9`.** Even for USD, converting through `Float` and truncating loses valid cents: my USD `"19.99"` probe passed 1,998 to the gateway instead of 1,999. This is independent of the currency-exponent defect. Parse and scale the decimal amount exactly, using integer minor units or decimal arithmetic with explicit precision handling.
